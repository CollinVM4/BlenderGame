# Plot-local turbine camera

`TurbineCameraController` is initialized by the existing client bootstrap. It
matches the local player's replicated `PlotSessionId` to a tagged `PlayerPlot`
with the same session, using TycoonService's existing assignment contract. Shared
session members therefore use their assigned workstation too. It does not infer
ownership from proximity or use a global camera marker.

The tagged plot registry updates on tag, ancestry and session changes. Each frame
checks the current character/root and three direct child lookups under the cached
plot. There are no per-frame workspace scans or touch/input listeners.

The root position is transformed into the zone's object space and compared to
its half-size on all three axes, including the boundary. Rotated zones work.
Entry uses Scriptable and a 0.3-second smoothstep CFrame interpolation from the
displayed view, then holds the authored camera CFrame. Focus follows the player.

Exit restores Custom and the current Humanoid, blending for 0.3 seconds toward
Roblox's live camera output. The controller preserves Roblox's unblended camera
between frames to avoid interpolation feedback. It uses callbacks immediately
before and after the [default camera render priority](https://create.roblox.com/docs/reference/engine/classes/RunService#BindToRenderStep).
Once the transition finishes it stops writing camera properties. Reentry starts
from the currently displayed view. Missing/replaced parts, death, character
removal, plot reset/reassignment, camera replacement and controller destruction
release camera ownership immediately; safety cleanup may skip the exit blend.

## Studio setup

Under **each plot's direct `Blender` child**, author these direct child BaseParts:

| Part | Anchored | CanCollide | CanTouch | CanQuery | Transparency |
|---|---|---|---|---|---|
| `TurbineCameraZone` | true | false | false | true | 1 |
| `TurbineCamera` | true | false | false | false | 1 |

Size and position the zone around the operating area, tall enough to contain the
HumanoidRootPart for supported avatar sizes. A thin floor pad will not contain
the root. Rotate/position the camera marker to frame the Blend-O-Meter, turbine
handle and player; its local forward direction defines the viewing direction.
The marker's size is irrelevant. No scripts, prompts or tags are needed on these
two parts. Existing PlayerPlot tagging and server session attributes are reused.
Absent or incorrectly typed parts disable the camera for that plot safely.
These authored parts are not generated by this feature or included in Rojo code.

## Validation

Run `python tests/run_turbine_camera_tests.py --luau <luau.exe>` for the isolated
presentation suite. It exercises translated/rotated bounds, both sides of every
axis, foreign plots, entry/hold/exit, live camera handoff, rapid reentry, inactive
noninterference, missing/replaced parts, root replacement, death/respawn, camera
replacement/destruction, session reassignment, streaming and teardown.

Focused camera tests, existing `client-presentation` and `plot-session` suites,
full-source Roblox-aware Luau LSP analysis, StyLua on changed Luau files, and Rojo
build pass. Analysis retains the existing CharacterPhysicsService
`LoadCharacterAppearance` deprecation warning.

CLI doubles do not render cameras or run Roblox's PlayerModule. Studio smoke
testing remains required:

1. Use two assigned plots/clients; entering another plot's zone must not activate.
2. Walk into/out of the zone, including rapid reversal during a transition. Check
   framing and rotation, normal camera orbit/zoom/collision after exit, first
   person and shift lock, and unchanged prompts/turbine interaction.
3. Repeat with touch and gamepad emulation and different aspect ratios/avatar
   sizes. Tune the authored marker/zone if necessary; no device-specific code is
   used.
4. Reset/respawn, replace a root, reassign/reset a session, stream/remove/recreate
   either marker or the plot, and replace CurrentCamera while active and exiting.
   Normal control must recover without remaining Scriptable.

No Studio play session was run as part of CLI validation. No gameplay, movement,
prompt, UI, FOV, or server-camera changes are included.
